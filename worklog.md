# Work log: SUBS-loop verification against the Sail ARM model in Rocq

Date: 2026-09-20
Machine: Linux (Ubuntu), opam switch `default` (OCaml 4.14.1), Rocq 9.2.0
Scope: this document describes exactly what was done and why. See `installation.md`
for how to reproduce the environment.

## 1. Goal

Machine-check two properties of a tiny hand-written ARM loop

    loop:  SUBS X0, X0, #1       ;  X0 := X0 - 1, set flags
           B.GT loop             ;  branch while X0 > 0

against the *actual* instruction semantics generated by Sail from the formal
Arm specification (`arm-v9.4-a`, the AArch64 model), not against a
hand-authored model:

- the register value strictly descends each iteration, while above zero
  (`loop_always_descends`),
- it never wraps below 0 (`loop_no_underflow`),
- the loop terminates — it reaches 0 in at most `uint X0` steps
  (`loop_terminates`/`loop_terminates'`).

The model is generated from
`rems-project/sail-arm` → `arm-v9.4-a/coq/armv9.v` (Rocq, i.e. Coq ≥ 9).
All proofs live in `/tmp/opencode/smoketest/loop.v` and compile in ~2 s with `rocq compile`.

## 3. The instruction semantics (what we proved against)

`SUBS Xd, Xn, #imm` with `imm = 1` is implemented by the model exactly as in
`v8_base.sail`:

    operand2 := not_vec (zero_extend imm 64)   -- bitwise NOT of the operand
    carry_in := 'b"1"                          -- subtract ⇒ borrow in = 1
    (result, nzcv) := AddWithCarry Xn operand2 carry_in

Facts pinned down in `armv9.v` (/ `Operators_mwords.v`, `MachineWord.v`, stdpp bitvector):

- `fst (AddWithCarry x y c) = autocast (integer_subrange (uint x + uint y + uint c) (N-1) 0)`
- `integer_subrange i 63 0 = autocast (subrange_vec_dec (mword_of_int i) 63 0)`
- `subrange_vec_dec v 63 0` = full-width `bv_extract` = identity on the unsigned value
- `uint w = Z.of_N (Z.to_N (bv_unsigned (get_word w)))`
- `uint (not_vec (zero_extend 1 64)) = 2^64 − 2`, `uint (carry_in) = 1`
- hence `uint x + (2^64−2) + 1 = uint x + (2^64−1)`, so

  `uint (sub_imm1 x) = (uint x − 1) mod 2^64`,
  and for `1 ≤ uint x` that is simply `uint x − 1` (modulus is no-op in range).

## 4. What we debugged (the important part)

1. **The full file used to hang the compiler (8+ min at 100% CPU / ~500 MB).**
   Root cause found by bisection: `vm_compute` (and `native_compute`-style
   reduction) on terms that contain **abstract variables** — e.g.
   `vm_compute; reflexivity` on a `bv` record equality with `v` symbolic, or
   `vm_compute in Hle` on `Z.of_nat v`. Fix: `vm_compute` is only applied to
   fully concrete/closed terms (numerals like `bv_modulus 64`, `uint ('b"1")`,
   `2^64 ≠ 0`). Loading the model is fast (2.1 s); the hang was purely the
   `vm_compute` calls.

2. **`rewrite` silently refuses subterms that are right there.**
   On this generated code, plain `rewrite` repeatedly failed with "Found no
   subterm matching" / "Candidate does not match" for terms visibly present
   (`uint (integer_subrange …)`, `Z.add_assoc`, `Z.mod_small`). Workaround:
   **`setoid_rewrite`** handles the same lemmas. Some `rewrite`s that did work
   earlier were left as-is.

3. **`reflexivity` on symbolic `mod` goals is unreliable after a prior `rewrite`.**
   `reflexivity`/`change`/`congruence` on `X mod m = X mod m` (X from a rewrite
   of `Z.mod_add`) fails with "No primitive equality found" / "Incomplete
   proof", while `unify` proves the sides convertible — a reduction-path quirk.
   Avoided by closing such steps with `apply (Z.mod_add …)` (which needs a
   `m ≠ 0` premise closed by `vm_compute; discriminate` on the concrete
   `bv_modulus 64`) and `apply (Z.mod_small …); rewrite bv_modulus64; lia`
   instead of reflexivity.

4. **A genuine arithmetic bug in the first draft**: `not_vec(1) + carry = 2^64 − 1`,
   not `2^64`. The old `uint_sub_imm1` claimed `18446744073709551614 + 1 = 2^64`,
   which is false; the constant is `…515 = 2^64 − 1` and
   `(uint x + (2^64 − 1)) mod 2^64 = (uint x − 1) mod 2^64` (lemma `sum_mod`).

5. **Notation/typing friction**: the `'b"1"` bitstring notation is
   *only-parsing* and unfolds to `N_to_word _ (Raw.to_N "1" N0) : mword 1`;
   `simpl` renders it as `N_to_word 1 (1 + 0)`. `uint (N_to_word …)` does not
   elaborate without a `: mword n` cast, so the concrete lemmas are stated in
   the unfolded form with explicit casts.

## 5. Proven results (in loop.v)

| item | statement |
|---|---|
| `uint_to_bv` | `uint x = bv_unsigned (get_word x)` |
| `uint_range` | `0 ≤ uint x < 2^64` |
| `uint_carry`, `uint_not_imm1` | `uint (carry_in) = 1`, `uint (operand2) = 2^64 − 2` (by `vm_compute`) |
| `slice_cancel_full`, `subrange_dec_full_uint` | full-width slice = identity |
| `uint_mword_of_int_mod` | `uint (mword_of_int 64 i) = i mod 2^64` |
| `integer_subrange_low64` | `uint (integer_subrange i 63 0) = i mod 2^64` |
| `sum_mod` | `(a + (2^64 − 1)) mod 2^64 = (a − 1) mod 2^64` |
| **`uint_sub_imm1`** | `1 ≤ uint x → uint (sub_imm1 x) = uint x − 1` |
| **`loop_always_descends`** | `0 < uint x → uint (sub_imm1 x) < uint x` |
| **`loop_no_underflow`** | `0 < uint x → 0 ≤ uint (sub_imm1 x)` |
| `descend` | `Fixpoint `descend k x` — the driver loop (at most k SUBS) |
| **`loop_terminates'`** | `uint x0 = Z.of_nat v → uint (descend v x0) = 0` (induction on v, bool-branch via `Z.leb_le`/`Z.leb_gt`) |
| **`loop_terminates`** | `0 ≤ uint x0 → uint (descend (Z.to_nat (uint x0)) x0) = 0` |

## 6. Method

Given the unusually fragile tool behaviour, no large-file edit was trusted.
Every lemma was first proven in a tiny scratch file in
`/tmp/opencode/smoketest/probe/`, compiled alone, then stitched into `loop.v`:

    rocq compile -R path/arm-v9.4-a/coq SailArm -o probe.vo probe.v

Hangs/errors were bisected with `timeout -k 1 N rocq compile …` and
`pkill -f "rocq compile"`. (Tool quirk worth knowing: `timeout N` alone lets
`rocq` survive — always use `-k` to SIGKILL.)

## 7. Scope, and what it does NOT cover

Proven: the arithmetic and control semantics of that one instruction sequence.

NOT covered, and not possible with this model as shipped:
- **Memory safety**: the model's loads/stores are *uninterpreted axioms*
  (`read_mem_`, `write_mem_`, `write_mem_` in `armv9.v:293-322`) — no address
  space, bounds, or allocation semantics to prove anything against. A safety
  proof would require hand-writing a memory layer in Coq first.
- **Race freedom**: the model is single-threaded sequential execution
  (interaction-tree events, one core). It contains no interleaving, memory
  ordering, or multi-core machinery. Race-freedom would need a separate
  hand-built concurrency model (e.g. Iris/OGS-style) on top of the ISA
  semantics.

Both are doable in principle with Rocq (general proof assistant; seL4/Iris/
CompCert precedent), but they are large, hand-written formalizations — not
something the Sail output gives you for free. "Run any assembly I write and
check it" is not a realistic Rocq workflow; a CFG/SMT model checker would be
the fit for that.
